1. The goal window                                                *lean-goal*

								  *:LeanGoal*
:LeanGoal		Open the goal window, or close it when it is open.
			<LocalLeader>g in a Lean buffer does the same.

The window follows the cursor through every Lean buffer and shows what Lean
knows about the place it is at: >

    Tactic state (2 goals)
    case left
    p q : Prop
    hp : p
    ⊢ p

    case right
    p q : Prop
    hp : p
    ⊢ q

    Messages
    6:46 error
    unsolved goals
    ...
<
"Tactic state" is the goals inside a `by` block, "Expected type" the type
of the term the cursor is in, and "Messages" every error, warning and
#eval or #check result whose text includes the cursor's line. A part with
nothing to say is left out. The window cannot be edited, and the cursor
never goes there by itself; it is an ordinary window otherwise, to scroll,
search and yank from. Beside the text when Vim is 130 columns or wider,
under it when not.

Which state ~
Lean answers for a position between two characters, and Vim's cursor in
Normal mode sits on one, so the position asked about is the left edge of
the cursor. On the first character of a tactic that is the state before the
tactic runs; anywhere further into it, the state after. So `^` on a line
shows what the tactic is given and `$` what it leaves. In Insert mode the
position is where the next character goes: at the end of a line, the state
after it, which is the goal to write the next tactic for.

Edits ~
The window shows the buffer as it is, saved or not. Lean is told of a change
when the cursor comes to rest, 80 ms after the last key, and elaborates the
file again from the change down. "Lean is working …" appears above the old
state when the answer takes more than a moment, as the first one in a
project with many imports will.

The server ~
The answers come from Lean's language server, `lake serve` in a Lake project
(|lean-make| says how one is found) and `lean --server` outside, run as a
|job| and spoken to over its stdin and stdout. One per project, started when
the window first needs it and never at startup, stopped when Vim exits.
It holds every open file elaborated in memory, imports included.

								*:LeanRestart*
:LeanRestart		Stop the servers and start again from nothing. For
			when Lean says the imports are out of date after a
			file this one imports was changed, and for a server
			that has died: one that stops by itself is not
			started again until asked, and the window says so.

								   *:LeanStop*
:LeanStop		Stop the servers. The next cursor movement in a Lean
			buffer with the window open starts one again.

Only the goal window is taken from the server. Completion, hover and jumping
to definitions are not, and |:make| does not go through it.

2. :make                                                          *lean-make*

|:make| checks the file being edited and puts Lean's errors and warnings in
the quickfix list. Write the file first: Lean reads it from disk.

A file on its own is checked with >
    lean "file.lean"
A file in a Lake project, one with a lakefile.lean or lakefile.toml in a
directory above it, is checked with >
    lake -d "project root" lean "file.lean"
which builds the file's imports first, so the first :make in a project that
uses Mathlib takes as long as that build does. Which of the two a buffer
uses is decided when it is opened; `:compiler lean` decides again.

An entry is the first line of a message: >
    Foo.lean|3 col 24 error| unsolved goals
    || ⊢ False
The lines under it, the goal, a hint or a note, are kept as they came, so
|:copen| shows a goal state laid out as Lean printed it, and |:cnext| steps
over them from one message to the next. The output of #eval and #check has
no position and is listed the same way.

Two things are put right after the list is read (lean#quickfix(), from a
|QuickFixCmdPost| autocommand). Lean counts columns from 0 and in characters,
Vim from 1 and in bytes, so the cursor lands on the right character of a line
with α and → before it. And when an import fails to build, Lake names that
file by its path from the project root, which is not the current directory;
the entry is pointed at the real file.

3. Symbols                                                     *lean-symbols*

In Insert mode a backslash and a name give a symbol, by the names Lean's own
editor support uses: >

    \to  →     \all  ∀     \and  ∧     \le  ≤     \<  ⟨     \a  α
    \l   ←     \ex   ∃     \or   ∨     \ge  ≥     \>  ⟩     \b  β
    \iff ↔     \fun  λ     \not  ¬     \ne  ≠     \.  ·     \N  ℕ
    \mapsto ↦  \|-   ⊢     \in   ∈     \times ×   \tr ▸     \1  ₁
<
							      *:LeanSymbols*
:LeanSymbols		List every name, by symbol, in a scratch window.

These are ordinary |:inoremap| mappings, local to the buffer. Where one name
begins another (\l and \le, \to and \top) Vim waits for the next key to tell
them apart, which in practice is the space or bracket typed anyway. No name
is a string escape, so "a\n" types as written, which is why × is \times and
↑ is \up. A backslash that must not start a symbol is typed |i_CTRL-V| \.

4. Colours                                                      *lean-syntax*

syntax/lean.vim knows comments (nested, and doc comments), strings, characters
and numbers, the keywords of commands and terms, the name after def, theorem,
structure, namespace and the like, @[attributes], the # commands, the options
of set_option, the holes ?_ and ?x, and the tactics.

The tactics are a fixed list, from Lean's parser table with Mathlib loaded,
kept by how Mathlib uses them; the comment above it has the rule. A new tactic
or a macro of your own stays plain until it is added there. left, right, symm
and trans are left out, as they are mostly ordinary names.

In colors/custom.vim the declared name and the tactics are lavender; strings
and characters light pink; escapes, the braces of s!"{x}", attributes, #eval,
options, holes, true and false light purple, and so are the logic of a
statement and the shape of a proof: quantifiers, connectives, arrows, ⟨ ⟩, the
focus dot and <;>. Hot pink is where Lean stops checking and nothing else:
`sorry`, `admit`, `stop`, `axiom`, `native_decide`, `unsafe` and `partial`.
Keywords, sorts, numbers and arithmetic stay plain.

The goal window has a syntax of its own, syntax/leangoal.vim, that marks its
shape and nothing in the text: headings lavender, `case` lines and errors
hot pink, the turnstile light purple.

5. The rest of the filetype plugin                            *lean-ftplugin*

'commentstring' and 'comments' for -- and /- -/, so |gq| formats comments
and gc (|comments|) toggles them. Two spaces of indent. ' is a keyword
character, so h' is one word to |star| and |w|. |%| matches ⟨ ⟩ and ⟦ ⟧.
|gf| on the Foo.Bar of an import opens Foo/Bar.lean under the project root.
|:MakeTags| knows Lean declarations (|tagsgen-languages|).

6. Options                                                     *lean-options*

Set these in the vimrc.

							  *g:lean_goal_auto*
g:lean_goal_auto	1 to open the goal window with the first Lean buffer,
			and so start a server for it. Default 0.

						      *g:lean_goal_position*
g:lean_goal_position	"right" or "below". Default: right when Vim is 130
			columns or wider.

				     *g:lean_goal_width* *g:lean_goal_height*
g:lean_goal_width	Columns for a window on the right. Default a third
			of the screen, 40 at least.
g:lean_goal_height	Lines for a window below. Default 12.

							 *g:lean_goal_delay*
g:lean_goal_delay	Milliseconds the cursor has to rest before Lean is
			asked. Default 80.

							*g:lean_symbol_maps*
g:lean_symbol_maps	0 to leave the symbol mappings out. Default 1.

						      *g:lean_symbol_leader*
g:lean_symbol_leader	What starts a symbol name. Default "\".

							     *g:lean_symbols*
g:lean_symbols		A dictionary of names to add or change. An empty
			symbol removes a name: >
    let g:lean_symbols = {'qed': '∎', 'o': ''}
<
